# 网络安全管理（网络安全风险管理报告）

## 1. 功能概述

按产品维护「网络安全风险管理报告」（章节树 JSON），覆盖视图分析与威胁建模、风险评估（含三类 RCM：内部/SBOM/网络安全扫描）、残余风险、维护更新、威胁缓解措施追溯；支持 Word 导入导出、复制版本（支持跨产品）、初始化模版。

> 与「风险管理报告」（45）独立并行——本模块面向 IEC 62304/IEC 81001-5-1 / FDA 网络安全要求，不复用 risk_mgmt_doc 模型与表，零耦合。

---

## 2. 用户操作流程

### 2.1 列表（`/cybersec_docs`）

按产品/版本筛选 → 新建空白 / Word 导入 / 复制版本（弹窗选目标产品，支持跨产品复制） / 编辑文件编号 / 导出 docx / 删除。
> 列表列宽与「风险管理报告」对齐：「文件编号」整列完整展示（不换行），「变更说明」列收窄。

列表列：产品名称、产品版本、报告版本、文件编号（单击编辑）、变更说明、创建时间、操作（查看/编辑/复制/导出/删除）。

### 2.2 详情（`/cybersec_docs/add | edit/:id | view/:id`）

章节树编辑、`content` JSON、附录矩阵（拉取产品 CST/RCM/HAZ）、导出 Word。

**新增模式选产品后自动联动**（`CybersecDocDetail.tsx`，仅 `isAdd`）：
- 选定产品+版本后，按 `selectedProductId` 自动拉取该产品的 CST（`list_prod_cst`）、RCM（`list_prod_rcm`）、HAZ（`list_prod_haz`），填充：
  - 4. 视图分析与威胁建模（4.5 STRIDE 等）的威胁矩阵；
  - 5.2 风险评估及控制措施（RCM）三类子节：内部 / SBOM / 网络安全扫描；
  - 7. 威胁缓解措施追溯。
- 自动填充文本章节（**仅当章节正文为空时填**，不覆盖手填）：
  - 「适用范围」← 产品 `scope`；「产品描述」← 产品名称/型号/完整版本；其它固定章节（目的、阶段活动、设计保证、异常情况响应、安全更新策略、用户指导、参考标准等）填入内置默认文案。
- 「初始化模版」按钮同样会用当前所选产品（若有）执行上述文本章节填充。

### 2.3 章节结构（`content.sections[]` 多级树，与源 Word 大纲一致）

> 标题采用 Word 原文；`ref_type` 绑定见括注。封面（cover）/ 文件修订记录（revision）为前置章节，不参与正文编号。

```text
1 概述
   1.1 目的
   1.2 产品描述
   1.3 适用范围
   1.4 系统架构和安全实现
      1.4.1 系统总体架构
2 阶段活动                               ← ref_type=stage_activity（阶段/开始/结束/结果 表）
3 关联文件
4 视图分析与威胁建模                       ← ref_type=view_analysis
   4.1 系统全局视图
      4.1.1 核心组件
      4.1.2 数据流和网络安全控制
      4.1.3 外部连接与安全影响
      4.1.4 外部节点的控制与信任边界
      4.1.5 安全控制映射
      4.1.6 威胁评估
   4.2 多患者危害视图
      4.2.1 安全措施
      4.2.2 非医疗功能引发的多患者危害场景
      4.2.3 攻击链与多患者风险路径图
      4.2.4 多患者攻击的响应与控制
      4.2.5 威胁分类
   4.3 安全用例视图
      4.3.1 目标作用
      4.3.2 用例分类与范围
      4.3.3 用例及威胁缓解
   4.4 可更新性视图
      4.4.1 更新类型与目标
      4.4.2 更新策略与流程
      4.4.3 更新频率与计划
      4.4.4 回退机制
      4.4.5 兼容性与依赖关系
      4.4.6 安全性与合规性
   4.5 威胁建模（STRIDE）
      4.5.1 威胁分类
      4.5.2 威胁评估                       ← ref_type=stride_threats（STRIDE 威胁矩阵）
5 风险评估
   5.1 风险评估评分标准                     ← 内置 CYBERSEC_SCORE_TABLE 5×5
   5.2 风险评估及控制措施（RCM）
      5.2.1 内部风险评估及控制措施           ← ref_type=cybersec_controls_internal
      5.2.2 SBOM风险评估及控制措施          ← ref_type=cybersec_controls_sbom
      5.2.3 网络安全扫描风险评估及控制措施     ← ref_type=cybersec_controls_scan
   5.3 残余风险评估
      5.3.1 残留风险结论                    ← ref_type=residual_risk
6 维护更新                                ← ref_type=maintenance
   6.1 设计保证
   6.2 异常情况响应
   6.3 安全更新策略
   6.4 用户指导
7 威胁缓解措施追溯                          ← ref_type=traceability（运行时计算）
```

## 5. 数据库表

共 **5 张**：`cybersec_doc`（content JSON）、`cybersec_threat`、`cybersec_control_internal`、`cybersec_control_sbom`、`cybersec_control_scan`（详见 [01_数据库表结构.md](./01_数据库表结构.md)）。

`cybersec_doc` 字段：
- product_id（必填）、version（必填）、file_no、change_log、content（JSON）
- 唯一约束：(product_id, version)

`cybersec_threat` 字段（仿 risk_analysis）：
- doc_id、product_id、threat_code（唯一/doc 内）
- view_type（string，4.x 子视图归属：全局/多患者/用例/可更新性/STRIDE）
- stride_category（string，4.5 STRIDE 类别）
- asset、description、attack_path、impact
- likelihood（SmallInt 1-5）、severity（string A-E 或 1-5）、risk_level（string：不可接受 / 可控 / 可接受）
- control_measures（TEXT）、rcm_codes（string 1024，关联控制措施编号串，跨三张 control 表查询）
- residual_likelihood、residual_severity、residual_level（同初始三项结构）

`cybersec_control_internal` / `cybersec_control_sbom` / `cybersec_control_scan` 字段（**三表结构同构、独立持久化**，仿 risk_control）：
- doc_id、product_id、rcm_code（**唯一/doc 内**，但跨三张表不互斥——业务上同一 rcm_code 不建议同时出现在多张表）
- description（TEXT）、threat_codes（string 1024，关联威胁编号串）
- verification_evidence（TEXT）、new_risk_flag（SmallInt 0/1）、note（TEXT）

> **为什么拆三张表**：网络安全 RCM 三类来源差异大——内部 RCM 来源于设计实现、SBOM 来源于第三方组件清单、扫描来源于工具报告，未来三类各自字段可能独立演化（例如 SBOM 行可能加 component_name/version/cve_id；扫描行可能加 scanner_name/scan_date）。拆表后扩展互不干扰；三表结构暂时同构，未来按需独立加列。

content 结构：`sections[]`（title, ref_type, text, tables, children, images）、productName、sourceWordPath。

ref_type 取值：cover、revision、stage_activity、view_analysis、stride_threats、cybersec_controls_internal、cybersec_controls_sbom、cybersec_controls_scan、residual_risk、maintenance、traceability、flow_diagram。

## 6. 关键业务逻辑与规则

1. **评分标准**：内置 `CYBERSEC_SCORE_TABLE`（5×5 likelihood × severity → 风险水平；红/橙/绿与 risk_mgmt_doc 的 RISK_ACCEPTANCE_TABLE 同图例但**独立常量**，不与之共享，方便后续按 IEC 62443 调整）。
2. **5.2 三类 RCM 拆三张表**：`cybersec_control_internal` / `cybersec_control_sbom` / `cybersec_control_scan` 各自独立 CRUD，对应章节 5.2.1（内部）/ 5.2.2（SBOM）/ 5.2.3（网络安全扫描）；前端 5.2 子节按 ref_type 选择对应端点。三表结构同构，不可合并。
3. **4.5 STRIDE 威胁矩阵**：`ref_type === stride_threats` 时表格行=`cybersec_threat where view_type='STRIDE'`。
4. **7. 威胁缓解措施追溯**：自动从 cybersec_threat 与三张 cybersec_control_* 表的 (threat_code ↔ rcm_codes / threat_codes) 关联渲染，**只读**展示，不入 DB（运行时计算，三张 control 表的结果合并展示并标注 source 列：内部/SBOM/扫描）。
5. 复制（支持跨产品）：列表「复制」弹窗选目标产品（默认当前产品），版本号自动生成、不允许手动填。
   - 同产品：`new_version(原版本)` 递增；跨产品：按目标产品现有最大版本 `new_version()` 递增，目标产品无文档则沿用原版本；撞号循环兜底递增，保证目标产品下 `(product_id, version)` 唯一。
   - 新文档 `product_id` = 目标产品；复制 `cybersec_threat` 与三张 `cybersec_control_*` 行时其 `product_id` 同步改为目标产品（`doc_id` 指向新文档）。
6. 删除文档：删关联 threat 与三张 control_* 行。
7. 选产品自动填充：见 2.2，文本章节「仅空时填」，动态矩阵区按 `selectedProductId` 实时拉取产品 CST/RCM。
8. **1.4.1 系统总体架构（`ref_type=flow_diagram`）自动获取网络安全流程图**：运行时按当前产品调用 `GET /doc_file/img_flow/list_doc_file?product_id=...`（图表文件管理的「网络安全流程图」`img_flow` 类别），取首条 `file_url` 以 `/{file_url}` 渲染，**只读、不可上传/更换**；无图时提示去「图表文件管理 → 网络安全流程图」上传。该节图片不取 Word 导入的 `section.images`。前端按 `ref_type===flow_diagram` 或标题以「系统总体架构」结尾兜底识别（兼容旧文档）。
9. **普通章节图片可上传/更换/删除**：除 `flow_diagram` 章节外，编辑模式下每张 `section.images` 图片可「更换/删除」，并可「上传图片」新增；图片以 base64 data URI 存入 `section.images`，随 `doSave` 落库（与 Word 导入存储一致）。查看模式只读展示。
10. **含「威胁编号」列的表格中 RCM 编号自动取产品 RCM 描述**：详情页加载/切换产品时，对**表头含「威胁编号」的表**，扫描单元格内的 `RCM\d+` 编号，按编号从 `list_prod_rcm`（当前产品 RCM）取 `description` 自动刷新单元格文本（多编号以空格拼接）。
    - 数据源严格为**产品 RCM**（`prod_id` 维度，无版本维度）；产品未关联该编号则**该单元格保持原样不动**（不清空、不丢数据），需先在「产品风险关联管理」给产品关联 RCM 才会命中刷新。
    - 刷新幂等：重复执行结果一致；命中刷新会覆盖该单元格手填文本（按需求设定为自动同步产品 RCM）。前端纯运行时处理，保存后随 content 落库。
11. **矩阵章节同时展示导入的原始表**：`stride_threats` / `cybersec_controls_*` / `traceability` 等矩阵章节，除渲染各自 DB 矩阵外，若 `section.tables` 有 Word 导入的原始表，则在矩阵下方以「导入的原始表」标题额外渲染（可编辑/加删行），避免导入数据被隐藏。矩阵（DB）与原始表（content）两者并存、各自独立。
    - **空矩阵隐藏**：当存在「导入的原始表」且对应 DB 矩阵无数据时，隐藏该空矩阵（避免冗余），只显示原始表。
    - **空矩阵不画空表**：矩阵无数据时仅保留「新增威胁/新增RCM」按钮，不渲染只有表头+「暂无」的空表（编辑模式）；有数据才渲染矩阵表。

## 7. 边界与特殊处理（重要：与产品 CST 的协同关系）

网络安全管理存在**两套并行**数据：
- `cybersec_doc.content`（JSON 章节）
- `cybersec_threat` / `cybersec_control`（结构化表）
- 产品 CST 实时数据（`list_prod_cst`）作为 4.5 STRIDE 威胁矩阵的**首选数据源**

详情页 4.5 STRIDE 矩阵主要来自 **`list_prod_cst`** + 文档内 `cybersec_threat where view_type='STRIDE'` 的并集，而不是仅 DB 矩阵表。

- Word 导入按标题归一化匹配模板章节；图片转 base64 写入 section；24 张表按章节路径 + 表序号映射到 `tables` 数组。
- 导出：产品名替换、附录表搬迁、评分标准图从 `sourceWordPath` 回填。

## 8. 修改注意事项 / 不可破坏的核心逻辑

1. **零耦合原则**：`cybersec_doc` 与 `risk_mgmt_doc` 是两套独立数据；不可在 `risk_mgmt_doc` 加 `type` 字段共用，也不可让 `cybersec_*` 反向引用 risk_mgmt 表。
2. **5.2 三类 RCM 拆为三张独立表**（cybersec_control_internal / _sbom / _scan），三表结构同构但独立持久化、独立 CRUD；不可合并为单表用 source_type 字段区分，也不可拆得更细（如把 SBOM 拆 component/license 两张）。
3. **CYBERSEC_SCORE_TABLE**（5×5）为合规内容，不可随意改动。
4. **4.5 STRIDE 矩阵以产品 CST 为权威**，与 `cybersec_threat` 表是补充关系，不可强制同步覆盖手填。
5. 删除文档级联删 threat 与三张 control_* 不可遗漏。
6. content 经 `__normalize_content` 规范化，保存前结构不可破坏。
7. **复制 `product_id` 为可选参数**，不传=同产品复制；跨产品复制时子表 `product_id` 必须同步为目标产品，否则残留旧产品 ID。
8. 选产品自动填充文本章节遵循「仅空时填」，不可改为覆盖手填内容。
9. 7. 威胁缓解措施追溯**运行时计算**，不入库不持久化，三张 control_* 表合并查询，结果带 source 列标识来源；威胁/控制更新后追溯实时反映。
