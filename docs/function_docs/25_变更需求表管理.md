# 变更需求表管理

> 本模块是 SRS 中最易出错、联动最复杂的部分（删除/保存/导入三方互相影响）。修改前**务必**通读「修改注意事项」。

## 1. 功能概述

变更需求表用于记录某次变更涉及的需求（编号+模块+功能+子功能）。每张变更表对应一条 `srs_type`（`type_code` 为 UUID 或 `change_xxx`，非 1/2），表内每行是一条 `srs_req`。变更表既存在于 `srs_type`/`srs_req`，也以表格节点形式存在于文档树（`srs_node`），并联动第 7 章功能描述。

---

## 2. 用户操作流程（SrsDocDetail）

1. **新增**：右上角「+ 新增变更表格」→ 打开同一弹窗「新增变更表格」（表名 + 四列表格，默认「变更需求N」、一行空数据）。点「保存表格」时由 `handleSaveChangeReqInCurrentPage` 在无 `type_code` 时调用 `add_srs_type`。取消不建表。
2. **编辑**：树内/区域内变更表「编辑」→ 同一 `EditableTableGenerator` 弹窗改行 → 保存 `handleSaveChangeReqInCurrentPage`。
3. **删除**：变更表「删除」→ `handleDeleteChangeReqTableInCurrentPage` → `delete_srs_type` + 清理文档树。

---

## 3. 前端实现

| 函数 / 组件 | 说明 |
|-------------|------|
| `openAddChangeTableModal` | 打开「新增变更表格」弹窗（表名 + 四列空行，尚未调 add_srs_type） |
| `handleSaveChangeReqInCurrentPage` | 保存变更表行；新增时无 type_code 则先 add_srs_type |
| `handleDeleteChangeReqTableInCurrentPage` | 删除变更表（核心，见下） |
| `EditableTableGenerator` | 新增/编辑共用弹窗（变更表隐藏行列/表头配置） |
| `fetchSrsTableState` | 变更表数据 = `list_srs_req` + `list_srs_type`，type_code 非 1/2 的 req 按 type 分组 |
| `matchesChangeTableTitle` | 表名匹配（含去章节号前缀后比较） |
| `isTreeChangeTableNode` | 判断树节点是否为变更表节点 |
| `dedupeChangeTableNodesInTree` | 去重同名变更表节点 |
| `syncChangeReqTablesToTree` | 用 DB 行覆盖树内变更表 rows（不删节点） |

---

## 4. 后端接口

| 方法 | 路径 | 入参 |
|------|------|------|
| POST | `/srs_type/add_srs_type` | SrsTypeForm{doc_id, type_name} → 服务端生成 `type_code=get_uuid()` |
| POST | `/srs_type/update_srs_type` | {id, type_name}（**不可改 type_code**） |
| DELETE | `/srs_type/delete_srs_type` | id |
| GET | `/srs_type/list_srs_type` | doc_id, 分页 |

---

## 5. 数据库表

- `srs_type`：doc_id, type_code, type_name（唯一 `(doc_id, type_code)`）
- `srs_req`：变更行，type_code 指向 srs_type.type_code
- 相关联动：`srs_reqd`（第 7 章）、`srs_node`（树内表格）、`sds_reqd`/`sds_trace`（若绑定 SDS）

---

## 6. 关键业务逻辑与规则

### 6.1 新增（add_srs_type）去重
- 同 `doc_id` 下 `type_name` 规范化后相同 → 直接返回已有记录（不重复建）。

### 6.2 删除（delete_srs_type）后端联动（核心）
1. 校验 `srs_type` 存在；**找不到直接报错**（避免前端用临时 id 误删却"假成功"）。
2. 删该 type 下全部 `srs_req` 及关联 `sds_reqd` / `sds_trace` / `srs_reqd`。
3. `__prune_change_table_nodes` — 删树中对应变更表节点：
   - 按 `type_name` **严格匹配**（`__matches_change_table_title`，等值或去章节号前缀后等值，**不做子串匹配**）。
   - 或整张表需求编号**全部属于**本次删除集合（`__table_codes_subset_of`）时按 code 删。
4. `__prune_req_detail_nodes_by_codes` — 删第 7 章下匹配 code 的功能描述节点。
5. `__prune_empty_req_chapter_shells` — 清理空壳 `7.x` / `__auto_req_group` 节点。

### 6.3 删除（前端 handleDeleteChangeReqTableInCurrentPage）
1. 从 `data.srsChangeTables` 找匹配表，取 `deletedRows`。
2. `resolveDeleteTypeId`：优先用真实 DB id（排除临时 id `>= 1e9`）；临时 id 时先 `list_srs_type` 按表名解析真实 id。
3. 乐观更新：先从 `srsChangeTables` 与树中移除该表。
4. 调 `delete_srs_type(id)`。
5. `reloadDocTreeAfterChangeTableDelete`：重新 `get_srs_doc` 拉树 + `fetchSrsTableState`；用 `stripDeletedChangeTableArtifacts` 兜底剥离该表节点与空壳；校验 DB 已无该表（`stillInDb` 则报错）。
6. 仅当树仍残留时才 `update_srs_doc` 持久化清理后的树（避免无谓重建）。

### 6.4 防止"删了又回来"（重要）
- **根因**：删表后若再 `update_srs_doc`，`__upsert_imported_change_req_tables_from_tree` 会从树上变更表节点重新插回 `srs_type`/`srs_req`。
- **对策**：删除流程优先信任后端 `srs_node` 清理结果；前端只在树确有残留时才持久化，并先剥离该表节点，避免 upsert 重建。

### 6.5 变更表数据不被树覆盖
- `__sync_srs_reqs_from_doc_tables` **跳过 type_code 非 1/2** 的行——保证保存普通内容时不会用树误改变更表 DB 数据。

### 6.6 变更表同步到树（__sync_change_req_tables_from_db）
- 从 DB 变更 req 重建/刷新树内变更表 `table.rows`；表名放 `table.name`，节点 `title` 不带章节号（避免被前端误判为章节）。
- 去重同名变更表；可 restructure 移动错位节点。

### 6.7 错分类迁移
- 变更 code 误存为 type 1/2 时，导入/保存兜底迁移到正确 change type（`__upsert_imported_change_req_tables_from_tree`）。

---

## 7. 边界与特殊处理

- **Word 导入的变更表**（标题如「2.0 变更需求列表：」、节点 title 形如「导入表格N」）需被保护：删除某张手动新增变更表时**不可误删** Word 导入表。前端 `isImportedChangeTableNode`（`导入表格N` 或 `^\d+(?:\.\d+)*\s+\S*变更` 标题）识别并保留。
- 前端 `pruneDetachedManualChangeTableNodes` 只清理"手动新增但 DB 已不存在"的孤儿节点，保留导入表。
- 临时 id（前端时间戳生成，`>= 1e9`）不可直接当作 `srs_type.id` 调删除接口。

---

## 8. 修改注意事项 / 不可破坏的核心逻辑

1. **后端 `__prune_change_table_nodes` 必须用严格表名匹配**（等值 / 去章节号前缀等值），**禁止子串匹配**（如「变更需求」⊂「变更需求列表」会误删 Word 导入表）。
2. **按 code 删除节点时，仅当整表 code 全属删除集合**才删（`__table_codes_subset_of`），避免误伤同章节其它变更表（如 307 与 308 互删）。
3. **删除后不要无条件 `update_srs_doc`**：会触发 `__upsert_imported_change_req_tables_from_tree` 重建。只有树确实残留时才持久化，且先剥离目标表节点。
4. **`__sync_srs_reqs_from_doc_tables` 跳过变更表（type_code 非 1/2）** 不可改动——这是变更表数据完整性的根本保证。
5. **前端 typeId 必须用真实 DB id**；临时 id（`>= 1e9`）须先 `list_srs_type` 按表名解析，否则后端找不到记录会"假成功"。
6. **Word 导入变更表保护**：`isImportedChangeTableNode` 识别的节点（`导入表格N` / 带章节号的"变更"标题）在删除其它表时不可被清除。
7. **add_srs_type 同名去重**不可移除（否则重复点击会建多张同名表）。
8. **update_srs_type 不可改 type_code**（type_code 是 srs_req 的关联键）。
9. 弹窗内"删单行后保存"与"外部删整表"是两条不同路径，互不干扰；修改一条时不要影响另一条。

## 9. 历史问题与修复记录（供回归参考）

| 现象 | 根因 | 修复要点 |
|------|------|----------|
| 删表后刷新又回来 | 删后 `update_srs_doc` 触发 upsert 重建 | 删后不无条件保存；先剥离节点再按需持久化 |
| 对应第 7 章功能描述章节删不掉 | 仅删 srs_type/srs_req，未删 srs_node 树节点 | `__prune_change_table_nodes` + `__prune_req_detail_nodes_by_codes` |
| 删 A 表误删 Word 导入表 | 表名子串匹配过宽 | 改严格匹配 + 整表 code 子集判断 + 导入表保护 |
| 删完多出一个空表 | 跨 type 误删后保存只剩空壳节点 | 按 type_name 精确匹配；前端清空壳 `removeEmptyMatchingChangeTableShells` |
| `delete_srs_type?id=` 传临时 id 假成功 | 前端用时间戳临时 id | `resolveDeleteTypeId` 用真实 id；后端找不到则报错 |
