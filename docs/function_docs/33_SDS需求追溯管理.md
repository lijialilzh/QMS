# SDS 需求追溯管理（sds_trace）

## 1. 功能概述

维护 SDS 设计与 SRS 需求的追溯关系（设计编号 sds_code、章节 chapter、位置 location），按需求展示为追溯表（图2 / 2.4 节）。一条需求对应多个设计编号或章节时，单元格内逐条换行，不单行裁切。

---

## 2. 用户操作流程

1. 树节点 `ref_type=sds_traces`（「2.4 设计与需求追溯表」）直接展示追溯表。标题旁不放「设计需求追溯」按钮。
2. 或 `SdsTraces.tsx` 独立页（未挂路由）。
3. 按产品 + SDS 版本查询；多行 SDS 编号会**展开**为多行。
4. 编辑：`sds_code`（必填）、`chapter`、`location` → `update_sds_trace`。

---

## 3. 前端实现

| 函数 | 说明 |
|------|------|
| `loadTraceListData()` | 弹框（要求先「获取SRS追溯」） |
| `syncTraceTableNodes()` | 用追溯数据刷新树内追溯表 |
| `expandTraceRows()` | 多行 sds_code/chapter/location 展开 + 合并单元格 |
| `buildVirtualLocationMap()` | 变更需求空 location 时虚拟章节推算 |

---

## 4. 后端接口

| 方法 | 路径 | 入参 | 返回 |
|------|------|------|------|
| GET | `/sds_trace/list_sds_trace` | prod_id, doc_id, type_code, from_sync, 分页 | Page[SdsTraceObj] |
| GET | `/sds_trace/get_sds_trace` | id | SdsTraceObj |
| POST | `/sds_trace/update_sds_trace` | SdsTraceForm | 成功/失败 |

`SdsTraceObj` 扩展：srs_code, name, module/function/sub_function, type_code/type_name, 产品/版本信息。

---

## 5. 数据库表

`sds_trace`：唯一 `(doc_id, req_id)`；字段 sds_code, chapter, location。

---

## 6. 关键业务逻辑与规则

### 6.1 自动补齐（__ensure_sds_traces，列表前调用）
1. 从 SRS「产品需求列表」读层级 `hierarchy_map`。
2. 必要时从 SRS Word 表补齐 `srs_req`/`srs_type`。
3. 对每个 `type_code != "reqd"` 需求 upsert 追溯行。
4. 删除已不在 SRS 的 req_id 追溯。
5. **RCN300 固定映射**（`FIXED_RCN300_TRACES`）：一条 SRS 可对应多个 SDS 编号+章节+location（产品特例）。对照认的是编号数字 `300-001`～`300-010`，不认死字母 RCN。其他需求把代号从 RCN 改成 ACN 后，仍用同一套对照：设计编号只把字母改成和需求编号一样（`SDS-ACN300-006`），模块名仍是对照里的名称（如 DLServer、RePACS、DataProcessing），不改成「性能要求」「基本要求」「图像处理」。一行里多条设计编号的先后不换。其他需求里删掉任意一条后，2.4 不再列出这一条，同号设计编号也不再出现在其他行。例如删掉 `SRS-ACN300-004` 后，`SRS-ACN300-003`、`SRS-ACN300-006` 里的 `SDS-ACN300-004` 一并去掉。打开详细设计或点获取 SRS 追溯时按当前还在的需求编号重取。展示和写回时不用需求上带数字后缀的中文名。单行也不用需求模块名覆盖。例如 `004` 写 DataProcessing，不写「图像接收」；`005` 写 RePACS，不写「图像存储」；编号仍是 `007` 时写 NeoViewer。其他需求不再套跨编号的历史对照：`001` 写当前模块名（如数据库要求），不写 RePACS；`002`、`003` 只写本行模块，不带 DLServer。删除需求规格后重新导入，再点获取 SRS 追溯，按当前其他需求重取，不恢复这套多行旧对照。法规符合性需求、外部连接、文档需求，以及新增的其他需求（如尾号 `011`），章节号都按当前 SDS 目录的实际章号写：先对设计编号，再对章节名。章号与左侧目录相同，封面、文件修订记录、目录不占号。目录里还没有对应章节时不编空号。不写死 8/9/10，也不用节点上错位的设计编号反推。文档需求和其他需求一样出现在 2.4 主表，设计编号由需求编号把 SRS 换成 SDS，名称写文档需求，章号按当前目录。
6. **2.4 主表行序**：标准需求和其他需求放在同一张主表，按需求编号的数字排，不看代号字母。编号去掉开头的 3 后比段号、序号：`300` 在前，然后 `301`，再是 `306`。`SRS-ACN300-001` 与原来的 `SRS-RCN300-001` 占同一位置，改字母不挪行。不把标准需求整组排到其他需求前面。变更需求仍在主表下方单独成表，表内行序与需求规格变更需求一致：先比代号中的数字，再比末段序号，如 `SRS-RCN308-001`、`SRS-RCN308-010`、`SRS-RCN308-012`、`SRS-RCN308-020`。打开编辑页和查看页都按这个顺序。
7. **设计编号自动获取**：其他需求的设计编号由当前需求编号把 SRS 换成 SDS，不再把 `001` 对到 `005` 这类旧编号。代号字母改了，设计编号只改同样的字母。图像显示、图像处理、图像存储、图像接收的编号离开原来的尾号后，这一行跟当前模块的英文名，不再用旧尾号对照。例如图像处理已删除、图像显示改成 `006` 时，这一行是 NeoViewer，不是 DLServer。数据库要求、性能要求、基本要求写当前模块名。删除需求规格并重新导入后，点获取不恢复历史多行对照。单元格里已有多行、且不是这套旧对照的手改编号不覆盖。
8. **其他需求设计编号可手改**：2.4 主表里，其他需求（`type_code=2`）的设计编号可以改，一行一个编号。没改过的仍按第 7 条自动取，第三列仍用原来的模块名和章号。改过之后（编号数字和自动结果不一样），其他需求的第三列只查当前追溯表和当前目录，不查 `300-004`～`007` 那张写死的英文对照。先找需求编号和这个设计编号是同一数字、且不是手改的那一行，用那一行已经显示的名称。例如 `006` 那一行是 NeoViewer（章节 5），在别的行再输入 `006`，也写 NeoViewer（章节 5）。找不到这一行时，再用当前目录里该编号所在章节的名字和章号。这两处都没有时，这一行留空，不写 DLServer，也不编空号。一行里多写的每一条设计编号都单独对。模块名或编号已经离开预置、第三列本来写着现在的模块名时，手改的设计编号仍保留，不再改回自动的那一条。输入框里的编号一变，第三列跟着变。标准需求的设计编号和第三列不能在这张表里改，名称仍按原来的规则取。
9. **章节号跟左侧目录**：2.4 主表「（章节 n）」用左侧目录正在显示的章号。封面、文件修订记录、目录不占号。目录把功能章排成 5.7.1.4 时，追溯表写 5.7.1.4，不用标题里留下的 6.7.1.4。

### 6.2 location 解析（非 from_sync）
1. DB 已存 location。
2. SDS 树按 `sds_code` 找节点 heading。
3. 按 module/function/sub_function 精确/模糊匹配树标题。
4. **NAME_DICT** 图像模块别名映射（如「图像处理」→ RePACS）。
5. 变更需求虚拟 location。

### 6.3 from_sync=true
- 直接用 DB 的 chapter/location，不做树推算。RCN300 固定映射除外，仍用映射里的名称和设计编号。法规符合性需求、外部连接、文档需求的章节号按当前目录实际章号。文档需求和其他需求一样显示在主表。

### 6.4 type_code 分组（追溯表渲染）
| type_code | 含义 | 位置 |
|-----------|------|------|
| 1 | 标准需求 | 主表 |
| 2 | 其他需求 | 主表 |
| 其它 | 变更需求 | extra_tables[] |
| reqd | 需求细节 | 不参与 |

---

## 7. 边界与特殊处理

- 无 SDS 树时仍展示 SRS 基础信息，便于手工编辑。
- RCN300 系列走固定 trace，跳过常规定位。

---

## 8. 修改注意事项 / 不可破坏的核心逻辑

1. **`from_sync` 两种取值的不同 location 来源**（DB vs 树推算）不可混淆。
2. **RCN300 固定映射 / NAME_DICT 别名** 为产品特例，改动会影响特定产品追溯。
3. **type_code 分组（主表 / extra_tables / 不参与）** 不可改。
4. 自动补齐时「删除已不在 SRS 的追溯」逻辑不可误删仍有效的行。
