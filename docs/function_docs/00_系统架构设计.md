# 系统架构设计

> 本文档描述 QMS（质量管理 / 需求追溯系统）的整体技术架构。所有结论均基于现有代码事实。

---

## 1. 系统定位

QMS 是面向医疗器械软件研发的**质量管理与追溯系统**，覆盖：产品管理、需求规格说明（SRS）、软件详细设计（SDS）、需求-设计-测试追溯、风险管理（HAZ/RCM/CST/DHF/风险报告）、测试集与测试用例、图表文件管理等业务域。

核心价值链：**产品 → SRS 版本 ↔ SDS 版本 → 追溯（需求/设计/测试/风险）**。

## 3. 后端分层架构

```
请求 → Middleware 链 → api 层 → serv 层 → model 层（SQLAlchemy）
                              ↓
                          obj 层（Pydantic DTO：tobj_*/vobj_*）
```

| 层 | 目录 | 职责 |
|----|------|------|
| **api** | `trace-api/src/api/` | HTTP 路由、参数校验、权限装饰器 `@try_log(perm=...)`、调用 serv、返回 `Resp` |
| **serv** | `trace-api/src/serv/` | 业务逻辑、SQL 查询/事务、文件保存 |
| **model** | `trace-api/src/model/` | SQLAlchemy ORM 表定义；基类 `Model` 含 `id/create_time/update_time` |
| **obj** | `trace-api/src/obj/` | Pydantic 模型：`tobj_*`（入参 Form）、`vobj_*`（出参 View）、`Resp`/`Page`/`Node`、`Perms`/`Roles` 枚举 |
| **utils** | `trace-api/src/utils/` | DB 上下文（sql_ctx）、i18n、工具函数 |

> api 与 serv 基本一一对应；部分 serv 被多个 api 共用（如 `serv_doc_file` 被 topo/struct/flow 三个路由复用，`serv_srs_doc` 解析逻辑被 SDS 导入复用）。

## 4. 应用初始化与中间件

入口：`trace-api/main_app.py` → `create_app()`（`trace-api/src/__init__.py`）

- **全局 context_path**：`/trace-api`
- **建表/初始化**：`trace-api/main_init.py` 用 `Base.metadata.create_all` 建表，并初始化角色/权限/管理员。

**中间件注册顺序（由外到内）：**
1. `AuthMiddleware` — 鉴权，注入 `CtxUser / CtxPerm / CtxLang`
2. `SessionMiddleware` — cookie `tx-session`，DB 后端 `DbBackend`
3. `CORSMiddleware` — `allow_origins=["*"]`，`allow_credentials=True`
4. `SQLAlchemyMiddleware` — 每请求一个同步 DB Session

**静态挂载：**
- `/trace-api/src-res` → Swagger 资源
- `/data.trace` → 上传文件目录

**白名单（免登录）：** `/.well-known/appspecific`、`/trace-api/src-res`、`/trace-api/user/login`、`/trace-api/user/logout`、Swagger 文档路径。

## 5. 鉴权与会话机制

1. **登录**：`POST /trace-api/user/login` → 校验 `MD5(pwd + pwd_sk)` → 写入 session `{user: uid}`（**不返回用户体**）。
2. **会话存储**：PostgreSQL `session` 表（key/value/exp/uid），cookie `tx-session`，`max_age=24h`。
3. **请求鉴权**：`AuthMiddleware` 从 session 取 uid → `serv_user.get_user` 加载用户及 `role_perms`。
4. **权限控制**：`@try_log(perm=Perms.xxx)` 检查 `CtxPerm`；`perm` 为列表时按 **OR** 校验（任一满足即可）。
5. **未登录**：返回 `code=-2`（HTTP 仍 200）；前端 `http.ts` 检测到 `-2` 跳转 `#/login`。
6. **密码**：`pwd_sk` 为时间戳盐；新用户/重置默认 `DEF_PWD`（环境变量，默认 `test`）；`ADMIN_NAME`（默认 master）受保护，不可被重置/删除。

> 角色与权限模型详见 [12_角色权限管理.md](./12_角色权限管理.md)。

## 6. 统一返回结构

```json
{ "code": 1, "msg": "请求处理成功!", "data": { } }
```

| code | 含义 |
|------|------|
| 1 | 成功 |
| 0 | 已知错误（业务/参数/权限） |
| -1 | 未知错误（异常捕获） |
| -2 | 未登录 / 会话失效 |

**分页结构 `Page<T>`：**
```json
{ "total": 100, "pages": 10, "rows": [], "page_index": 0, "page_size": 10 }
```

- HTTP 层**始终 200 OK**（含校验失败、未登录、异常）；文件导出返回二进制流。
- 参数校验失败：`code=0`，`msg=请求参数错误:{字段名}`。
- 时间统一格式化为 `%Y-%m-%d %H:%M:%S`。

## 8. 前后端交互

- **开发**：Vite proxy 将 `/trace-api`、`/data.trace` 代理到 `URL_API`（`.env` 默认 `http://localhost:18080`）。
- **生产**：OpenResty（Nginx）将 `/trace-api/` 反代到 trace-api 容器，`/data.trace` 静态 alias。
- **前端封装**：`trace-web/trace/src/api/http.ts`（fetch + JSON/文件下载）；各模块 `ApiXxx.ts` 前缀 `/trace-api/{module}/...`。
- **文件上传**：`FormData`；**下载**：检测 `content-type` 为 octet-stream / docx。

## 11. 文档树通用结构（重要基础设施）

SRS / SDS / 风险报告均采用「文档主表 + 节点树」模型：

- 通用节点字段（`obj/node.py` 及各 `*_node` 表）：`doc_id, n_id, p_id, priority, title, label, text, ref_type, img_url, table(JSON)`，SRS 额外有 `srs_code/rcm_codes`，SDS 额外有 `sds_code`。
- **保存策略**：整树提交，后端先删全部节点再重建（详见各模块文档与 [01_数据库表结构.md](./01_数据库表结构.md)）。

## 12. 修改注意事项 / 不可破坏的核心逻辑

1. **统一返回结构**：任何接口都必须返回 `{code,msg,data}` 且 HTTP 200；前端依赖 `code` 判断（尤其 `-2` 跳登录）。不可改为 HTTP 4xx/5xx 返回业务错误。
2. **中间件顺序**：Auth → Session → CORS → SQLAlchemy 的注册顺序不可随意调整，否则鉴权/会话/DB 上下文会失效。
3. **context_path `/trace-api`**：前端所有 API 路径都基于此前缀，改前缀需同步前端 `http.ts` 与代理。
4. **整树重建保存**：`update_*_doc` 删后重建是既定策略，相关「保存后同步」副作用（见 SRS/SDS 文档）依赖此前提，不可改为增量更新而遗漏副作用。
5. **会话表 `session`**：是 starlette-session 的 DB 后端，**不要**手动改其结构。
