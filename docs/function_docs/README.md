# QMS 功能设计文档（功能基线）

> 本目录是**整个系统的功能基线文档**，作为后续开发、修复 Bug、模型/人员交接时的**唯一标准**。
>
> 核心约定（与项目根目录 `.cursorrules` 一致）：
> 1. 所有开发、修复、调试，**必须以本目录文档为准**，不得脱离文档凭代码反向猜测、重构、改动业务逻辑。
> 2. 文档未提及的逻辑、流程、判断、分支，一律**保持原样**，绝不改动。
> 3. 改 Bug 只允许**分步、局部**修改文档中明确指定的范围，不影响其它已实现功能。
> 4. 每份功能文档底部均有「修改注意事项 / 不可破坏的核心逻辑」，修改前必须先读。

## 关键全局概念速查

### type_code（srs_req.type_code）语义

| 值 | 含义 |
|----|------|
| `"1"` | 标准/产品需求（模块+功能+子功能） |
| `"2"` | 其他需求（模块+对应章节，无功能/子功能列） |
| `"reqd"` | 独立新增功能描述时创建的占位需求行 |
| 其它（UUID / `change_xxx`） | 变更需求表，每个对应一条 `srs_type` |

### ref_type（节点引用类型）

- SRS：`img_struct`、`img_flow`、`img_topo`、`srs_reqs`、`srs_reqs_1`、`srs_reqs_2`、`srs_reqs_x`、`srs_reqds`
- SDS：`img_struct`、`img_flow`、`img_topo`、`sds_traces`、`sds_reqds`
- 风险报告：`cover`、`revision`、`participants`、`acceptance_standard`、`risk_analysis`、`risk_controls`

### n_id（文档树节点 ID）

- 文档主表 `n_id` 记录当前已分配的最大节点 ID。
- `update_srs_doc` / `update_sds_doc` 保存策略：**先删除文档全部节点，再整树重建**；提交前会重置前端携带的旧 `n_id`（新节点用 0）。

## 文档维护规则

1. **新增功能**：先在本目录补功能文档，再写代码。
2. **修复 Bug**：先在对应文档「修改注意事项」中确认不会破坏现有逻辑，再分步改代码。
3. **文档与代码不一致**：以文档为准；若确属文档遗漏，需先更新文档并标注变更日期。
