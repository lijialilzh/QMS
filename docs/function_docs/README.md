# QMS 功能设计文档（功能基线）

> 本目录是**整个系统的功能基线文档**，作为后续开发、修复 Bug、模型/人员交接时的**唯一标准**。
>
> 核心约定（与项目根目录 `.cursorrules` 一致）：
> 1. 所有开发、修复、调试，**必须以本目录文档为准**，不得脱离文档凭代码反向猜测、重构、改动业务逻辑。
> 2. 文档未提及的逻辑、流程、判断、分支，一律**保持原样**，绝不改动。
> 3. 改 Bug 只允许**分步、局部**修改文档中明确指定的范围，不影响其它已实现功能。
> 4. 每份功能文档底部均有「修改注意事项 / 不可破坏的核心逻辑」，修改前必须先读。

## 关键全局概念速查

### type_code（srs_req.type_code）语义

| 值 | 含义 |
|----|------|
| `"1"` | 标准/产品需求（模块+功能+子功能） |
| `"2"` | 其他需求（模块+对应章节，无功能/子功能列） |
| `"reqd"` | 独立新增功能描述时创建的占位需求行 |
| 其它（UUID / `change_xxx`） | 变更需求表，每个对应一条 `srs_type` |

### ref_type（节点引用类型）

- SRS：`img_struct`、`img_flow`、`img_topo`、`srs_reqs`、`srs_reqs_1`、`srs_reqs_2`、`srs_reqs_x`、`srs_reqds`
- SDS：`img_struct`、`img_flow`、`img_topo`、`sds_traces`、`sds_reqds`
- 风险报告：`cover`、`revision`、`participants`、`acceptance_standard`、`risk_analysis`、`risk_controls`

### n_id（文档树节点 ID）

- 文档主表 `n_id` 记录当前已分配的最大节点 ID。
- `update_srs_doc` / `update_sds_doc` 保存策略：**先删除文档全部节点，再整树重建**；提交前会重置前端携带的旧 `n_id`（新节点用 0）。

## 《功能逻辑 & 开发文档》编写规范（全局强制标准）

> 适用范围：本目录下**所有功能逻辑 / 开发类文档**，均须遵循统一的 8 模块固定结构。
> 模板文件：[`_TEMPLATE_功能逻辑开发文档.md`](./_TEMPLATE_功能逻辑开发文档.md)（新建文档时复制它）。

### 一、固定结构（不得删减 / 改名 / 简化 / 调序）
每份功能逻辑文档必须且只能包含以下 8 个模块，顺序与编号固定：

1. **功能概述**：用途、使用场景、最终目标、关联上下游功能。
2. **前置依赖 & 关联模块**：涉及页面、组件、接口、状态仓库、公共方法；并标注【只读 / 禁止修改】模块清单。
3. **完整执行流程（分步细化）**：从触发入口起，按执行顺序写每一步的「动作 → 入参 → 内部逻辑 → 数据变化 → 调用链路 → 页面表现」；所有分支（if / 判断 / 多选 / 多入口）单独列出走向。
4. **核心规则 & 判定条件**：所有布尔判断、过滤规则、权限校验、状态判断逐条写明「规则原文 + 含义 + 不满足后果」。
5. **数据结构说明**：核心字段、含义、默认值、取值范围、数据流转规则。
6. **异常场景 & 兜底逻辑**：报错、为空、重复、删除/编辑失败、并发刷新、权限不足、网络异常等的处理。
7. **功能约束 & 修改红线**：允许修改范围、绝对禁止改动的逻辑/函数/文件、禁止新增逻辑、禁止重构结构。
8. **验收标准**：逐条可勾选验收点，满足即正常、不满足即为问题。

### 二、写作硬性要求
- 完全脱离代码也能看懂，不依赖翻阅源码。
- 语言直白、逻辑线性；步骤连续编号（1./2./3.），分支用「分支A / 分支B」标注。
- 不贴大段代码；必要时仅标注关键函数名 / 文件路径（如 `serv_srs_type.py::delete_srs_type`）。
- 引用数据库表 / 接口字段时，链接到 01、02~06 文档，不重复粘贴整表。
- 文档头部必须含元信息表（功能编号、所属模块、主要代码位置、文档版本、最后更新）。

### 三、执行顺序约定
1. **先文档后代码**：任何新增 / 修复 / 迭代，先按本模板补齐或更新对应功能文档，并经确认后再动代码。
2. **改动以文档为准**：开发 / 修复严格落在文档「7. 功能约束 & 修改红线」允许范围内，红线内容一律不动。
3. **存量文档迁移**：现有功能文档（10~53）逐步迁移到本 8 模块结构；新建文档一律直接套用模板。

## 文档维护规则

1. **新增功能**：先在本目录按模板补功能文档，再写代码。
2. **修复 Bug**：先在对应文档「7. 功能约束 & 修改红线」中确认不会破坏现有逻辑，再分步改代码。
3. **文档与代码不一致**：以文档为准；若确属文档遗漏，需先更新文档并标注变更日期。
